## Focus Areas

### UX（用户感知层面）
- **定义**：用户从启动到完成核心流程（建连 / 保存 / 切 tab）过程中的摩擦
- **检查方式**：
  - 错误信息文案含"接下来做什么"操作建议（grep 错误码 → 文案）
  - 长操作（连接 / 上传 / 同步）有进度反馈
  - 设置项 self-explanatory（无悬空 label / 占位符）
  - 首次启动有引导（首次启动 banner / 引导页 / 示例连接）
- **证据**：具体 error msg 文案 / 设置项截图 / 引导流程缺失位置
- **不做什么**：不审视觉设计（颜色 / 间距）/ 不审 icon 设计 / 不审键盘快捷键冲突

### 文档完整性
- **定义**：用户 / 贡献者能通过文档独立完成「安装 → 配置 → 使用 → 贡献」
- **检查方式**（每个文件需存在 + 含实质内容）：
  - `README.md` — 含 Install / Quick Start / Screenshots / FAQ
  - `README_zh-CN.md` — 中文版是否存在并与英文版同步
  - `CONTRIBUTING.md` — 含 Dev Setup / Test / Style Guide / PR Process
  - `CHANGELOG.md` — 按 [Keep a Changelog 1.0+](https://keepachangelog.com/zh-CN/1.1.0/) 规范，含 `Added / Changed / Deprecated / Removed / Fixed / Security` 段
  - `LICENSE` — 文件含 license 名 + 持有者 + 年份
  - Screenshots/GIFs — 核心流程（建连 / 终端 / AI 侧边栏 / Kubernetes）
  - Code 内公开 API 注释 / godoc 完整
- **证据**：缺哪个文件 / 哪段缺失 / 哪个流程无截图
- **不做什么**：不审翻译准确性 / 不审 doc 阅读体验

### i18n 完整性
- **定义**：所有面向用户的字符串（UI 文案 / 错误 / 提示）有 9 locale 翻译，且 key 一致
- **检查方式**：
  - `frontend/src/i18n/locales/` 下 9 个 locale 文件 key 集合一致（用 `jq` / `sort` 对比）
  - 组件硬编码中文 / 英文（grep `>[一-龥]{{<` 或 `'[A-Z][a-z]+ [a-z]+'` 字符串）
  - missing key 在 UI 露出 key 本身（`{{ $t('xxx') }}` fallback 不当）
- **证据**：locale 文件 diff / 硬编码位置 / 漏翻译 key 列表
- **不做什么**：不审术语统一性 / 不审文案风格

### 功能完整性（无空 stub）
- **定义**：菜单 / 按钮 / 设置项 / 协议列表的所有承诺都有真实实现
- **检查方式**：
  - 菜单项点击后无反应（grep `onClick={() => {}}` / `// TODO` 路径）
  - 协议列表 (`backend/session/`) 命名 vs 实现一致
  - 文档承诺的功能 vs 代码存在性（README 提到但 `grep -r` 找不到）
  - 占位符 / 空状态页面
- **证据**：空函数位置 / 承诺与实现差异
- **不做什么**：不审功能设计本身 / 不审是否应该存在

### 一流 OSS 标准（外部贡献者角度）
- **定义**：让外部贡献者能 submit issue / PR / 找到项目元信息 / 遵守行为准则
- **检查清单**（每个 grep / ls 验证）：
  | 项目 | 应在 | 验证命令 |
  |---|---|---|
  | Bug 报告模板 | `.github/ISSUE_TEMPLATE/bug_report.md` | `ls .github/ISSUE_TEMPLATE/` |
  | Feature 请求模板 | `.github/ISSUE_TEMPLATE/feature_request.md` | 同上 |
  | PR 模板 | `.github/PULL_REQUEST_TEMPLATE.md` | `ls .github/` |
  | 贡献指南 | `CONTRIBUTING.md` | `wc -l CONTRIBUTING.md`（应 > 50 行） |
  | 行为准则 | `CODE_OF_CONDUCT.md` | 参考 [Contributor Covenant 1.4+](https://www.contributor-covenant.org/) |
  | 安全披露 | `SECURITY.md` | 含 contact + timeline |
  | 依赖自动升级 | `.github/dependabot.yml` 或 `.github/renovate.json` | `ls .github/dependabot*` |
  | README 徽章 | build status / coverage / license | grep `![` in README.md |
  | 第三方 license | `frontend/src/assets/third-party-licenses.txt` 或构建脚本生成 | find `*-licenses*` |
  | Issue label 规范 | `.github/ISSUE_TEMPLATE/` 关联的 label 文件 | `ls .github/labels*` |
- **证据**：缺哪项 / 不符合哪条规范
- **不做什么**：不审 PR review 流程 / 不审 issue triage 流程 / 不审 governance（governance 是组织层）

### 可达性 / 命名一致性
- **定义**：键盘可达、颜色对比、aria-label、跨页面命名一致
- **检查方式**：
  - 关键按钮无 `aria-label`（grep `el-button` 无 `@keydown.enter` 等）
  - 颜色对比 < 4.5:1（暗色主题文字）
  - 同概念不同名（如「保存」vs「提交」在多个组件里混用）
- **证据**：具体组件 + 命名不一致位置
- **不做什么**：不审 WCAG 全规范 / 不审屏幕阅读器全场景

### ⚠️ 为什么 location 不能只给 file:line

- **行号会漂移**：commit / 格式化后行号变，下游 AI 找错位置
- **section 名更稳定**：跨 commit 改 section 名几率低
- **code_block 给完整上下文**：AI 直接读懂，不用再 grep
- **caller_chain 给影响面**：修复时要同步更新所有 caller
- **test_target 给具体落点**：不用 AI 猜
- **verification 给可执行命令**：AI 验证 fix 真有效

每条 finding 同步更新 6 个矩阵（`matrix/{coverage,severity-category,risk-impact,verification,milestone-map,role-lens}.md`）。

## 评估维度（每条 finding 必填）

### ROI（修复投入产出）
- **修复成本**：人时（小 / 中 / 大）+ 风险（低 / 中 / 高：跨文件 / 破坏 API / 数据迁移）
- **修复收益**：用户价值（高频 / 中频 / 低频）+ 频次（每天 / 每周 / 偶尔）+ 不可替代性（独家卖点 / 通用能力）
- **修复紧迫性**：是否阻塞用户主流程 / 是否反复修 / 是否被客诉

### 问题复杂度（修复难度分层）
- **技术复杂度**：跨文件数 / 跨包数 / 是否需要 schema 迁移 / 是否需要新依赖
- **业务复杂度**：影响多少用户群 / 影响多少核心 user journey
- **测试复杂度**：需要多少 mock / fixture / 跨 OS / 跨平台

### 多角度判断（不同视角的修复必要性）
- **用户视角**：用户能否感知 / 是否影响首次体验 / 是否影响留存
- **开发者视角**：是否阻碍未来开发 / 是否影响 onboarding / 是否反复踩坑
- **业务视角**：是否影响市场推广 / 是否影响付费转化 / 是否影响合规
- **安全视角**：是否构成攻击面 / 是否泄露用户数据
- **长期视角**：技术债积累速度 / 未来重构成本

### 优先级判断流程（填到 finding 的 Context / Suggested Fix）
1. ROI 高 + 复杂度低 → **必修**（直接进 P1 修复）
2. ROI 高 + 复杂度高 → **排期修**（进对应 milestone）
3. ROI 低 + 复杂度低 → **有空修**（放 backlog）
4. ROI 低 + 复杂度高 → **谨慎评估**（可能不做）

每条 finding 在 Context 中说明属于上述哪个象限 + 原因。

## 问题生命周期（每条 finding 必走完整流程）

**不要只写「找到问题」就完事**。每条 finding 必须走完 5 步：

### 1. 多次确认（多次独立审计）
- **目的**：避免误报 / 假阳性 / 误解
- **做法**：
  - 至少 **3 次独立确认**：grep 一次 + 读代码一次 + 调用链反查一次
  - 每次确认要写明「用什么命令 / 读了哪些行 / 反查到什么 caller」
  - 3 次结论不一致 → **不算 finding**，改写或撤回
- **证据格式**：`Confirmation: [1] grep pattern → matches N, [2] read lines X-Y → confirms Z, [3] reverse caller check → A→B→C`

### 2. 问题上下文分析（必填 Context 段）
- **不是「哪里出错」而是「为什么是问题」**：
  - 触发条件（什么场景下用户会撞到）
  - 影响范围（多少用户 / 多少流程 / 多少设备）
  - 当前缓解措施（用户如何 workaround / 是否已部分修复）
  - 长期影响（不修会怎样：技术债积累 / 用户流失 / 合规风险）
- **不要写**：「这里有 bug」「这里不完整」 — **要写**：「用户在 X 场景做 Y 操作时，会触发 Z 结果，导致 W 问题，长期累积 V 后果」

### 3. 技术方案（必填 Suggested Fix 段）
- **要给出可执行方向，不要只说「应改进」**：
  - 修改哪些文件 / 哪些函数
  - 改动的粒度（单行 / 单函数 / 单文件 / 跨文件）
  - 备选方案（如果主方案不行，可以走哪条路）
  - 依赖与风险（是否需要新库 / 是否破坏 API / 是否要 migration）
- **不要写**：「重构」「优化」「加固」 — **要写**：「在 `xxx.go:NNN` 的 `func Foo()` 内将 `A` 改为 `B`，调用方不变，备选方案：在 `xxx.go:MMM` 加 helper，统一 5 处类似调用」

### 4. 问题验证测试（Reproduce Test — Fix 之前）
- **目的**：写一个测试，证明 bug **存在**（这个测试应当 FAIL 当前代码）
- **写法**：
  - 触发条件：具体输入 / mock / fixture
  - 断言：期望结果（应当发生但实际未发生）
  - 不依赖什么：网络 / 数据库 / 时间（除非必要）
- **示例**：Failing test `Test_Reproduce_F001_IPv6_Dial`：构造 `host="::1", port=8080`，调用 `dialAddr`，断言返回 `"[::1]:8080"`，当前实现返回 `"::1:8080"`（FAIL）
- **不要跳过这步**：没有 reproduce test 的 finding = 没有证据链完整

### 5. 修复效果测试（Fix Verification — Fix 之后）
- **目的**：写一个测试，证明 fix **生效**（这个测试应当 PASS 修复后代码）
- **写法**：
  - 同 reproduce test 触发条件
  - 断言：期望结果（现在应当发生且实际发生）
  - 回归断言：现有合法输入仍正常（防止 fix 引入新 bug）
- **示例**：Passing test `Test_Fix_F001_IPv6_Dial`：修复后 `dialAddr("::1", 8080)` 返回 `"[::1]:8080"`（PASS），且 `dialAddr("127.0.0.1", 8080)` 返回 `"127.0.0.1:8080"`（回归 PASS）

### 输出格式（追加到 finding 末尾）

```markdown
## Confirmations
- [1] grep -rn 'TODO' backend/ | wc -l → 47 处
- [2] 读 backend/session/manager.go:120-145 → 确认 3 处未实现
- [3] 调用链反查 → app.Connect → session.Manager → nil 处理缺失

## Reproduction Test
\`\`\`go

    // 触发 bug 的最小输入
    // 断言期望（应当失败）
}
\`\`\`

## Fix Verification Test
\`\`\`go

    // 同触发条件
    // 断言期望（应当通过）
    // 回归断言（合法输入仍正常）
}
\`\`\`
```

## 子任务产物自审（写完所有 finding 后必跑一遍）

- 所有 finding 都通过 5 步 lifecycle（确认 / 上下文 / 方案 / 验证测试 / 效果测试）

- 自审发现的问题（如有）→ 修后再交付

## ⚠️ 重要约束（audit 模式铁律）

- **测试 / 检查脚本写出来即可**，**不必实际执行**
- **修复方案只写文档**，**不实际修改代码 / 不实际写新文件**
- **每条 finding 落盘后由人工 review 再决定是否执行**
