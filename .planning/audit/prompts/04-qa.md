## Focus Areas

### 覆盖缺口（按 package 扫描）
- **定义**：每个主要 package 应有 `_test.go` + 行覆盖 ≥ 60% + 分支覆盖 ≥ 50%
- **本项目 package 清单**：

| Package | _test.go 现状 | 优先级 | 备注 |
|---|---|---|---|
| `backend/session/` | 部分（已有 sshtest / telnet_test 等） | 中 | 13 个协议实现，每协议应有 |
| `backend/store/` | 部分 | 中 | 多个 store 文件 |
| `backend/database/` | 部分 | 中 | provider + engine + executor |
| `backend/k8s/` | 部分 | 高 | Manager 复杂状态 |
| `backend/container/` | 部分（runner_local_test / runner_ssh_test 等） | 中 | 多 OS 实现 |
| `backend/sync/` | **0 测试**（F-007） | **高** | 加密云同步风险大 |
| `backend/platform/` | **0 测试** | 中 | 字体 OS 差异 |
| `backend/log/` | **0 测试** | 低 | 文件日志简单 |
| `backend/update/` | **0 测试** | 中 | 应用内更新 |
| `backend/ai/` | 不详 | 中 | LLM 客户端 |
| `backend/terminal/` | 不详 | 中 | 终端公共逻辑 |

- **检查方式**：
  - `find <pkg> -name '*_test.go' | wc -l` 看数量
  - `go test -coverprofile=cover.out ./<pkg>/` 看行覆盖
  - `go tool cover -html=cover.out` 看未覆盖代码块
- **证据**：pkg 名 + 当前覆盖 + 缺失测试 function 名
- **不做什么**：不审覆盖率阈值是否合理 / 不审是否值得测

### 边界用例
- **定义**：每个 public function 应测空 / 超大 / 并发 / 超时 / 取消 / 网络错误 / 编码 / 数值边界 / 时区
- **检查清单**（每个 function 测试设计时应考虑）：
  | 输入维度 | 测试用例 |
  |---|---|
  | 空输入 | `""` / `nil` / `[]` / `map{}` |
  | 超大输入 | 1MB string / 1M slice / 100k map |
  | 并发 | 100 goroutine 同时调用 |
  | 超时 | 100ms 限时函数 |
  | 取消 | `ctx.Done()` 触发取消 |
  | 网络错误 | DNS 失败 / connection refused / timeout |
  | 编码 | UTF-8 / GBK / binary / invalid UTF-8 |
  | 数值边界 | 0 / 1 / -1 / MaxInt / MinInt / NaN / Inf |
  | 时区 | UTC / Local / +08:00 / DST 边界 |
- **证据**：function 名 + 缺失的边界类型
- **不做什么**：不审特定边界值（具体数字留给 Developer）

### 回归风险
- **定义**：核心路径修改后能否被现有测试捕获
- **检查方式**：
  - 最近 100 commit 修改的 function 是否有测试
  - migration / schema 变化是否有 migration test
  - 跨 OS 兼容性测试（macOS / Linux / Windows CI）
  - 跨 Go 版本测试（1.21 / 1.22 / 1.23）
  - 前端 vitest + e2e 覆盖度
- **证据**：commit 列表 + 缺测的核心路径
- **不做什么**：不审 commit message 规范 / 不审 PR review 流程

### AC 可验证性
- **定义**：PRD 写的 Acceptance Criteria 是否有可执行的验证手段
- **检查方式**：
  - PRD / README 提到的承诺（如「连接池」「自动重连」「密码加密」）→ 是否有 e2e 测试
  - 用户文档描述的功能 → 是否有手动验证脚本
  - 核心 user journey（建连 / 保存 / AI 助手 / Kubernetes）→ 是否有端到端测试
- **证据**：AC 列表 + 缺失验证手段
- **不做什么**：不审 AC 写得好不好 / 不审产品需求本身

### 测试基础设施
- **定义**：测试 helper / fixture / mock / fuzz / race detector / CI 配置
- **检查方式**：
  - `testutil/` 包存在性与覆盖
  - mock 框架（gomock / testify / sqlmock）一致性
  - race detector CI 开关
  - fuzz test 存在性（`FuzzXxx` 函数）
  - coverage gate（CI 拒绝覆盖率下降）
- **证据**：缺失的工具 + 应加的位置
- **不做什么**：不审测试命名规范 / 不审 assertion 风格

### Bug 历史
- **定义**：反复修的 bug / FIXME / HACK / XXX 注释反映的隐性回归
- **检查方式**：
  - `git log --all --oneline | grep -i 'fix\|hotfix\|regression'` 看反复修的模块
  - `git blame` 找最近 5 commit 都改过的 function
  - FIXME / HACK 注释（grep `grep -rn 'FIXME\|HACK' backend/`）
- **证据**：模块名 + 修过的次数 + 当前 HACK 标记
- **不做什么**：不审 bug 修复质量本身 / 不审 issue 历史

## 评估维度（每条 finding 必填）

### ROI（修复投入产出）
- **修复成本**：人时（小 / 中 / 大 — 写一个测试通常 < 1h）+ 风险（低 / 中 / 高）
- **修复收益**：未来 regression 拦截次数（高频 / 中频 / 低频）+ 不可替代性（e2e 唯一 / 多重覆盖）
- **修复紧迫性**：是否已知 bug 在该路径上反复出现 / 是否近期要重构该模块

### 问题复杂度（修复难度分层）
- **测试设计复杂度**：需 mock 多少依赖 / 多少 fixture / 是否需要真实数据库 / 是否需要网络
- **跨环境复杂度**：是否跨 OS / 跨 Go 版本 / 跨数据库
- **覆盖率深度**：行覆盖 / 分支覆盖 / e2e 覆盖 / fuzz 覆盖

### 多角度判断（不同视角的修复必要性）
- **用户视角**：bug 出现频率（每天 N 次 vs 偶尔 1 次）/ 严重程度（崩溃 vs 体验差）
- **开发者视角**：未来重构信心 / 改这个 function 时能否快速验证 / 是否敢动这块代码
- **业务视角**：合规要求（金融 / 医疗 测试必需）/ 客户合同承诺
- **安全视角**：未测试代码是否构成安全漏洞（SQL / XSS / 认证）
- **维护视角**：测试本身是否易维护 / 是否依赖外部脆弱资源

### 优先级判断流程（填到 finding 的 Context / Suggested Fix）
1. ROI 高 + 复杂度低 → **必修**（直接进 P1 修复）
2. ROI 高 + 复杂度高 → **排期修**（进对应 milestone）
3. ROI 低 + 复杂度低 → **有空修**（放 backlog）
4. ROI 低 + 复杂度高 → **谨慎评估**（可能不做）

每条 finding 在 Context 中说明属于上述哪个象限 + 测试用例设计（断言 / mock / 不依赖）。

## 问题生命周期（每条 finding 必走完整流程）

**不要只写「这里没测试」就完事**。每条 finding 必须走完 5 步：

### 1. 多次确认（多次独立审计）
- **目的**：避免误报 / 假阳性 / 误解
- **做法**：
  - 至少 **3 次独立确认**：grep 测试文件一次 + 读目标函数一次 + 跑 coverage 一次
  - 每次确认要写明「用了什么命令 / 读了哪些行 / 当前覆盖率多少」
  - 3 次结论不一致 → **不算 finding**，改写或撤回
- **证据格式**：`Confirmation: [1] find backend/sync -name '*_test.go' | wc -l → 0, [2] read backend/sync/git.go:50-80 → 关键函数 0 测试, [3] go test -cover ./backend/sync/ → 0.0%`

### 2. 问题上下文分析（必填 Context 段）
- **不是「没测试」而是「没测试会导致什么 bug」**：
  - 触发条件（什么场景下会触发未覆盖的代码路径）
  - 影响范围（多少用户 / 多少流程会撞到未测代码）
  - 当前缓解措施（是否有手动测试 / 是否有 workaround）
  - 长期影响（不补测试会怎样 — 回归无拦截 / 重构不敢动 / bug 反复出现）
- **不要写**：「缺测试」 — **要写**：「backend/sync/crypto.go 的 AES-GCM 加解密函数未测，未来若改 key derivation 算法，将无法被回归测试拦截，可能静默破坏加密同步」

### 3. 技术方案（必填 Suggested Fix 段）
- **要给出具体测试用例设计**：
  - 测试哪些 function / 哪些路径
  - 用什么 mock / fixture（明确不依赖什么 — 不依赖网络 / 不依赖真实数据库 / 不依赖时间）
  - 断言什么（具体输入 → 期望输出）
  - 边界覆盖（空 / 超大 / 并发 / 错误路径）
- **不要写**：「加测试」 — **要写**：「在 `backend/sync/crypto_test.go` 加 `TestEncryptDecrypt_RoundTrip`：固定 password="test-key-123"，plaintext="hello world"，断言 Encrypt 后 Decrypt 回原文；加 `TestDecrypt_WrongPassword`：错误 password 应返回 error 而非 panic；不依赖网络 / 不依赖真实文件系统（用 `t.TempDir()`）」

### 4. 问题验证测试（Reproduce Test — Fix 之前）
- **目的**：写一个测试，证明当前实现 **未被覆盖**（用 coverage profile / mutation test 体现）
- **写法**：
  - 写一个 minimal test，**当前应当 FAIL**（如果补了断言当前实现的某段代码）
  - 或跑 `go test -coverprofile` 看 0% 覆盖
  - 或跑 `go-mutesting` 看 mutation 漏检
- **示例**：Failing test `Test_Coverage_BackendSync`：当前 `go test ./backend/sync/ -cover` 输出 `coverage: 0.0% of statements`，目标 ≥ 70% → FAIL
- **不要跳过这步**：没有 baseline coverage 的 finding = 没法证明补完测试后真提升

### 5. 修复效果测试（Fix Verification — Fix 之后）
- **目的**：写一个测试 + 跑 coverage + 跑 mutation，证明补完测试 **真的拦截回归**
- **写法**：
  - 同 reproduce 触发条件（跑同一测试套件）
  - 断言：coverage 达到目标（行 ≥ 70% / 分支 ≥ 60%）
  - 断言：mutation score 提升（跑 `go-mutesting`，mutation 存活率 ≤ 30%）
  - 回归断言：现有测试仍全绿（防止新测试破坏旧行为）
- **示例**：Passing test 套件 + `go test -cover` 输出 `coverage: 72.0% of statements` 达到目标 → PASS

## ⚠️ 重要约束（audit 模式铁律）

- **测试代码写出来即可**，**不必实际跑 / 不必构造 mock**
- **修复方案只写文档**，**不实际写测试文件 / 不实际加 mock / 不实际改 CI 配置**
- **每条 finding 落盘后由人工 review 再决定是否落地测试**
